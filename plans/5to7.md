## Why a separate direct jump

It checks that the step-by-step path did not depend on 6.x stepping stones, and it is the path the real module
would take. The work is done **from the 5.6 code, without copying from `hibernate-6-to-7`**. At the end the two 7.3
code bases are diffed and the differences explained under "Results".

## What a direct jump hits (and the step-by-step path softens)

- **No deprecation trail.** `Session.save/saveOrUpdate/update/delete`, `@Cascade(SAVE_UPDATE)`,
  `Table.getUniqueKeyIterator/getForeignKeyIterator`, `SQLServer2012Dialect`, `HANACloudColumnStoreDialect` were
  not deprecated in 5.6 (or only mildly), and are **gone** in 7 → straight compile errors.
- **Silent behaviour changes accumulate:** native `COUNT(*)` `BigInteger` → `Long` (6.0); native date →
  `LocalDate` (7.0); native-query errors no longer wrapped in `PersistenceException` (6.0); unset column
  length/precision/scale `255/19/2` → `null` (6.0); `new Table(String)` sets the contributor, not the name (6.0);
  `scroll()` without a mode fails when JDBC metadata access is off (6.x); MySQL metadata dialect throws
  `RuntimeException` instead of `JDBCException` (Tools 6).
- **Removed with no direct replacement:** `AbstractScrollableResults.getResultSet()` (6.0), `SessionImpl.connection()`
  (6.0), `SimpleValue` generator getters (7.0), Tools' `ReverseEngineeringRuntimeInfo`/`SQLExceptionConverter` access.

## Results (2026-10-07)

**Done.** The port was made by a separate agent in its own clone, from `main` + the shared baseline-fix commit, the
plans and the research notes only — it did not see `hibernate-6` / `hibernate-6-to-7`. Re-verified afterwards:
`./gradlew clean build` 0 compiler warnings, `./gradlew run` all 8 Mains OK, the re-generated `run-output.txt` is
byte-identical to the committed one, no local paths in history.

**Comparison with the step-by-step result (`hibernate-6-to-7`, same 7.3.13 target):**
- **Behaviour: identical.** Diffing the two `run-output.txt` files with notes/headers removed leaves only
  presentation differences: the same SQL, statement counts, query results, cascades, dialect versions, exception
  types and messages, reverse-engineered model and generated files.
- **API choices: the same everywhere** — both independently chose `getSqlType(Metadata)`, `getForeignKeyCollection()`,
  JPA `cascade` + reflective look at the deprecated Hibernate `CascadeType`, `find`, `createMutationQuery` /
  `createNativeMutationQuery`, typed native queries, `scroll(FORWARD_ONLY)`, `getPosition()`, `doWork`/`doReturningWork`
  + `ResultSetMetaData` for row 35, `getJdbcCoordinator()` for row 31, `DdlTypeRegistry.getTypeName(int, Size, Type)`,
  no-arg `HANADialect`/`SQLServerDialect`, `MetadataDescriptorFactory` + Boolean `PREFER_BASIC_COMPOSITE_IDS`, a local
  `SchemaSelection` implementation, try-with-resources around `addInputStream`, `RevengDialect.configure(ConnectionProvider)`,
  `SqlExceptionHelper` in the custom metadata dialect, `ExporterConstants` properties.
- **Differences (style / presentation):** the direct port prints Tools' java.util.logging warnings in the slf4j-simple
  format instead of only raising the level; row 34 prints the `HIRED_ON` type once instead of per row; row 35 uses
  `doReturningWork` and prints the column count; row 47 also prints `new Table("DEPARTMENT").getName()` → `null`;
  different note wording; `columnNames(Collection)` vs `(List)`; local variables vs repeated `getProperties()`.
- **One substantive difference — row 14:** the direct port reads the id generator from
  `PersistentClass.getIdentifier()` (an `EnhancedValue`), which reports **`foreign`** for `EMPLOYEE_DETAIL` (shared
  primary key with `EMPLOYEE`). The step-by-step port read it from the id column's value, which for that table is the
  `OneToOne` (no generator getters in 7; 5.6/6.6 printed its default, `assigned`, which was misleading). The direct
  port's approach is better and is back-ported to `hibernate-6-to-7` and `hibernate-7.4`.

Conclusion: the 6.x stepping stone did not hide or add anything — going straight from 5.6 to 7.3 needs exactly the
changes listed in this plan; the direct jump's only extra cost is that nothing was deprecated first (straight compile
errors).

Open issues: none.
